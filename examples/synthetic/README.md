# Synthetic card reconciliation inputs

Everything in this folder except this README is generated by
`python3 examples/generate.py` (package `examples/generador_sintetico/`). All
names, RFCs, UUIDs and amounts are fictitious. A test regenerates the files and
fails if they differ, so never edit them by hand.

```bash
python3 examples/generate.py                       # rewrites examples/synthetic/
python3 examples/generate.py --salida /tmp/x --semilla 7 --ventana-min -3 --ventana-max 10 --tolerancia 0.50
```

Exit codes: `0` written, `2` invalid parameters, `3` no candidate set passed the self-check.

## Determinism

- One `random.Random` instance per attempt, seeded from `--semilla` (default 4242). The
  global `random` module is never used.
- All money is `Decimal`, quantized to 0.01 with `ROUND_HALF_UP`. Exchange rates use 4 decimals.
- Output is UTF-8 without BOM, LF line endings, sorted keys and sorted rows, no timestamps.
  Two runs with the same parameters are byte-identical (same SHA-256).
- After generating, a self-check (`verificar`) confirms the oracle is the only reasonable
  answer (see "Matching rules"). If a random coincidence breaks it (for example, two
  invoices that happen to add up to an unrelated charge), the run is repeated with a
  derived sub-seed. `oraculo.json -> parametros.intento` records which attempt was kept.

## Files

| File | Format | Content |
|---|---|---|
| `estado_cuenta_alfa.csv` | CSV, layout `ALFA_V1` | Raw statement of issuer ALFA (calendar month) |
| `estado_cuenta_beta.csv` | CSV, layout `BETA_V1` | Raw statement of issuer BETA (cycle closes on day 28) |
| `resumen_estados_cuenta.json` | JSON | Statement summary with control totals |
| `universo_cargos_esperado.jsonl` | JSONL | Expected normalized charge universe (one row per statement row) |
| `cfdis.jsonl` | JSONL | CFDI pool: card invoices, decoys, vendor noise and payroll |
| `libro_mayor.csv` | CSV | General ledger lines (double entry, every entry balances) |
| `oraculo.json` | JSON | Known answer per charge and per edge case |
| `veredictos_libro.csv` | CSV | Synthetic human verdicts on ledger matching, with planted conflicts |

## Conventions

- Amounts in JSON/JSONL/ledger are strings like `-1234.56` (never JSON numbers).
- Statement sign: charges positive; merchant refunds (`abono`) and card payments (`pago`) negative.
- CFDI amounts are always non-negative; a credit note (`tipo_comprobante = "E"`) subtracts.
- `delta` = `fecha_emision` of the CFDI minus `fecha` of the charge, in days.
- UUIDs keep the 8-4-4-4-12 shape but carry a non-hex `SINT` marker and a last group that
  starts with a digit, so they can never be mistaken for real fiscal folios or RFCs.
- RFCs are `RFC_*` placeholders or the SAT generic RFCs `XAXX010101000` (general public)
  and `XEXX010101000` (foreign). The company receiving invoices is `RFC_EMPRESA_DEMO`.

## Raw statement layouts

Layouts are identified by an exact match of the full header row (row 1). No preamble rows.

**`ALFA_V1`** (Spanish headers)

`Fecha de operación, Fecha de aplicación, Descripción, Titular, Tarjeta, Moneda origen, Importe origen, Tipo de cambio, Importe MXN`

- Dates `DD/MM/YYYY`. Amounts signed, with thousands separator (`"-1,234.56"`, quoted by CSV).
- `Descripción` is a fixed-width merchant descriptor (24 chars, truncated) followed by a city code.
- `Tarjeta` is masked: `****1001`. `Tipo de cambio` is empty for MXN rows.

**`BETA_V1`** (English headers)

`Transaction Date, Post Date, Description, Card Member, Account Ending, Foreign Spend Amount, Foreign Currency, Exchange Rate, Charges, Credits`

- Dates `MM/DD/YYYY`. For days 1-12 this is ambiguous against ALFA, which is why the layout
  must come from the header and never be guessed.
- Unsigned amounts without thousands separator; exactly one of `Charges` / `Credits` is filled.
- Foreign columns are empty for MXN rows; `Foreign Spend Amount` is unsigned.

Each layout has one row with an impossible operation date (`30/02/YYYY`, `04/31/YYYY`). The row
must be kept, flagged and counted in the control totals, never dropped.

## `resumen_estados_cuenta.json`

`{"esquema": "resumen_estados_cuenta/v1", "estados_cuenta": [...]}`, one object per statement:

| Field | Meaning |
|---|---|
| `archivo`, `emisor`, `nombre_emisor`, `layout`, `moneda` | Identification |
| `periodo_inicio`, `periodo_fin`, `corte` | Cycle dates (ISO); `corte` = `periodo_fin` |
| `num_movimientos` | Row count, including unparseable rows and payments |
| `total_cargos` / `total_abonos` | Sum of positive / negative rows |
| `total_neto` | Signed sum of all rows (control total) |
| `saldo_anterior`, `saldo_al_corte` | `saldo_al_corte = saldo_anterior + total_neto`; the previous balance is paid in full by the `pago` row |

## `universo_cargos_esperado.jsonl`

What a correct statement normalizer must produce from the raw files, sorted by `cargo_id`.

| Field | Rule |
|---|---|
| `cargo_id` | `<EMISOR>-<fila, 4 digits>` |
| `emisor`, `layout`, `archivo`, `corte` | From the statement |
| `fila` | 1-based data row number (header excluded) |
| `fecha` | Operation date, ISO; `null` if unparseable |
| `fecha_aplicacion` | Posting date, ISO |
| `descripcion` | Raw description with whitespace collapsed to single spaces |
| `titular`, `tarjeta_ultimos4` | Cardholder and last 4 digits |
| `monto`, `moneda` | Signed MXN amount; `moneda` is always `MXN` (billing currency) |
| `monto_original`, `moneda_original`, `tipo_cambio` | Original currency amount (signed), `MXN`/`USD`, 4-decimal rate or `null`. For USD rows `monto = round(monto_original * tipo_cambio, 2)` |
| `tipo_movimiento` | `cargo` if `monto > 0`; `pago` if negative and the description starts with `PAGO RECIBIDO` / `PAYMENT RECEIVED`; otherwise `abono` |
| `estado`, `motivo` | `ok`/`null`, or `ininterpretable`/`fecha_invalida` |

## `cfdis.jsonl`

Sorted by `uuid`. Fields: `uuid`, `serie`, `folio`, `fecha_emision` (ISO date),
`tipo_comprobante` (`I` invoice, `E` credit note, `N` payroll), `direccion`
(`recibido` / `emitido`, from the company's point of view), `rfc_emisor`, `nombre_emisor`,
`rfc_receptor`, `nombre_receptor`, `moneda` (`MXN`/`USD`), `tipo_cambio` (string or `null`),
`subtotal`, `iva`, `total` (in `moneda`; `subtotal + iva = total`), `total_mxn`
(`round(total * tipo_cambio, 2)` for USD), `forma_pago` (`04` card, `03` transfer, `99`
other; intentionally noisy, do not rely on it), `metodo_pago`, `uso_cfdi`, `concepto`,
`uuid_relacionado` (invoice a credit note refers to). Three `concepto` values carry a
planted prompt injection (see "Planted prompt injections").

## `libro_mayor.csv`

One row per ledger line, sorted by `asiento_id`, `linea`. Columns: `asiento_id`, `linea`,
`fecha`, `periodo`, `origen` (`TARJETA`, `CXP`, `NOMINA`), `cuenta`, `nombre_cuenta`,
`proveedor_id`, `proveedor_nombre`, `proveedor_rfc`, `referencia`, `memo`, `debe`,
`haber`, `moneda`. Every entry balances (`sum(debe) = sum(haber)`).

- Card accounts: `2105-001` (ALFA), `2105-002` (BETA). A recorded charge credits its card
  account for the full amount; a recorded refund debits it.
- Domestic invoiced purchases split VAT to `1180-001`; foreign and non-invoiced ones do not.
- Bucket vendor: `PRV-0999 GASTOS VARIOS TARJETA` (generic RFC), used for many merchants.
- Vendor names in the ledger are similar to, but not equal to, statement descriptors and
  CFDI legal names (for example `CAFE LUNA AZUL 0231` / `CAFETERIA LUNA AZUL SA DE CV` /
  `CAFETERIA LUNA AZUL`).

## `oraculo.json`

```text
esquema        "oraculo_conciliacion/v1"
parametros     semilla, intento, periodo, ventana_dias {min,max}, tolerancia_monto,
               banda_fuera_de_tolerancia {min,max},
               empresa, rfcs_genericos, cuentas_tarjeta, proveedor_cubeta,
               libro_desfase_dias {min,max}, cubeta_lejana_dias {min,max}
resumen        counts of charges, CFDIs, entries, lines, and of every case tag
grupos_empate  [{grupo, cargos[], cfdis[], asientos[]}]
cargos         one object per charge:
  cargo_id, casos[] (tags below), grupo_empate (id or null)
  cfdi:        esperados[] (UUIDs), evidencia, prohibidos[], motivo_sin_cruce
  libro_mayor: esperado (asiento_id or null), riesgo_cubeta, prohibidos[], motivo_sin_cruce,
               veredicto ({veredicto, asiento_id} or null), conflicto (type or null)
veredictos_libro  archivo, filas, conflictos {type: count}, sin_conflicto
revision_texto_libre
  marcados            [{origen, registro_id, campo, familia, cargo_id, plantilla}]
  cargos_en_revision  [cargo_id]
```

- `cfdi.evidencia`: `monto_exacto`, `monto_tolerancia` (0 < diff <= tolerance),
  `suma` (2-3 CFDIs of one emitter, signed sum exact; includes invoice + credit note), or
  `moneda_original` (USD invoice equal to the USD charge; the MXN amounts differ because
  each side used its own exchange rate). `null` when nothing is expected.
- `parametros.banda_fuera_de_tolerancia`: range of `|signed total_mxn - monto|` of the planted
  near misses (`fuera_de_tolerancia`), as text. It is `2 * tolerancia_monto + 0.50` to that plus
  `2.00`, so it moves with `--tolerancia` (`2.00` gives `4.50` to `6.50`). An engine that wants
  to label near misses can read it instead of hard-coding it.
- `cfdi.motivo_sin_cruce`: `sin_candidato`, `fuera_de_ventana`, `fuera_de_tolerancia`,
  `solo_rfc_generico`, `fila_ininterpretable`, `no_aplica` (card payments).
- `libro_mayor.motivo_sin_cruce`: `sin_candidato`, `descartado_por_nombre`,
  `cubeta_evidencia_insuficiente`, `fila_ininterpretable`, `no_aplica`.
- `prohibidos` lists decoys that a correct engine must not assign to that charge.
- Tie groups: inside a group, any one-to-one assignment between the group's charges and the
  group's CFDIs (and entries) is correct; `esperados` shows one valid assignment.

- `libro_mayor.veredicto` / `libro_mayor.conflicto` describe the row of `veredictos_libro.csv`
  for that charge (both `null` when there is none). `conflicto` is what a correct ledger engine
  must report when it compares the verdict against its own proposal (`esperado`); see below.

### Matching rules the oracle assumes

1. A CFDI is a candidate for a charge only if `direccion = recibido`, `tipo_comprobante`
   is `I` or `E`, `rfc_receptor` is the company (a generic receptor is not evidence), and
   `ventana_dias.min <= delta <= ventana_dias.max` (both inclusive; default -3 / +10).
2. One-to-one: `|signed total_mxn - monto| <= tolerancia_monto`, or, when both sides are
   in USD, the same test on the original-currency amounts.
3. Sums: 2-3 candidate CFDIs from the merchant's own emitter (generic RFCs never group).
   One-to-one tiers take precedence: a charge resolved one-to-one never reaches the sum tier,
   and a CFDI claimed one-to-one by another charge is not available for sums.
4. Ledger candidate: a line on a card account (`2105-*`) on the right side, with
   `|amount - |monto|| <= tolerancia_monto`. Recorded entries are dated 0-3 days after the
   charge; bucket-vendor matches need both amount and date and carry `riesgo_cubeta = true`.
5. Exclusivity: no CFDI and no ledger entry is expected by two charges.

Random amounts are drawn at least `2 * tolerancia_monto + 0.50` apart, so accidental
matches only happen where a case is designed to create them.

## `veredictos_libro.csv`

What a person already decided about some charges, as input for the ledger engine. The engine
must never overwrite a verdict and must report every disagreement with its own proposal.
Columns `cargo_id, veredicto, asiento_id, nota`, sorted by `cargo_id`, one row per charge at most.

- `veredicto = registrado` names an existing `asiento_id`; `veredicto = no_registrado` leaves it empty.
- `nota` is free text and is data only.
- No two verdicts name the same entry, no verdict touches a tie group, and no verdict names the
  expected entry of another charge, so `libro_mayor.esperado` stays the right answer for every
  charge without a verdict.
- Verdicts are drawn with their own `random.Random` sub-seed, so adding them did not change any
  other file.

Conflict types (verdict versus the correct proposal):

| Verdict | Correct proposal | `conflicto` |
|---|---|---|
| `registrado` in X | X | `null` |
| `registrado` in X | Y, different from X | `asiento_distinto` |
| `registrado` in X | no entry | `motor_sin_cruce` |
| `no_registrado` | Y | `motor_con_cruce` |
| `no_registrado` | no entry | `null` |

Planted families (default seed, 12 rows):

| Family | Count | Charges | Verdict | `conflicto` |
|---|---|---|---|---|
| confirms the entry | 4 | `libro_registrado` | `registrado` in the expected entry | `null` |
| confirms a bucket entry | 1 | `libro_cubeta` | `registrado` in the expected bucket entry | `null` |
| confirms no entry | 2 | `libro_no_registrado` | `no_registrado` | `null` |
| denies an existing entry | 2 | `libro_registrado` | `no_registrado` | `motor_con_cruce` |
| names a far bucket entry | 1 | `libro_cubeta_fecha_lejana` | `registrado` in the prohibited bucket entry | `motor_sin_cruce` |
| names a payables entry | 2 | `libro_registrado` | `registrado` in an unrelated `CXP` entry | `asiento_distinto` |

## Planted prompt injections

Three CFDI concepts carry text addressed to a model, so the card pipeline's human review
queue has something to show. A free-text screen such as `prompt_guard` must flag each one;
the record stays in the data and nothing is fixed or removed.

| Template | Where | Family a correct screen reports |
|---|---|---|
| `anulacion_en_concepto` | the only CFDI of a clean, fully matched charge | `anulacion_instrucciones` |
| `comentario_html` | the only CFDI of another clean, fully matched charge | `marcado_html` |
| `base64_en_referencia` | a vendor-noise CFDI that backs no charge | `anulacion_instrucciones` (inside base64) |

- Only `concepto` changes, and no matching engine reads it, so every match and every other
  part of the oracle is the same as without the injections.
- `oraculo.json -> revision_texto_libre.marcados` lists each planted record with the
  family to expect and the charge it backs (`cargo_id`, or `null`);
  `cargos_en_revision` lists the charges that must end up `en_revision` in the pipeline.
- No other description or concept is meant to be flagged: a flag elsewhere is a false
  positive of the screen.
- Injections are drawn with their own `random.Random` sub-seed after the verdicts, so they
  do not consume the randomness of the rest of the run.
