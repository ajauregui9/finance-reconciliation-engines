# Synthetic Amazon settlements

Everything in this folder except this README is generated by
`python3 examples/generador_amazon` (package `examples/generador_amazon/`). Seller, SKUs,
order ids and amounts are fictitious. A test regenerates the files and fails if they differ,
so never edit them by hand.

```bash
python3 examples/generador_amazon                          # rewrites examples/synthetic_amazon/
python3 examples/generador_amazon --salida /tmp/x --semilla 7 --pedidos-por-mes 60
```

Exit codes: `0` written, `2` invalid parameters, `3` the self-check found a designed
scenario that did not come out as intended.

## Determinism

One `random.Random` seeded with `--semilla` (default 2026); the global `random` module is
never used. Money is `Decimal`, quantized to cents with `ROUND_HALF_UP`. Output is UTF-8
without BOM, LF line endings, sorted JSON keys, no timestamps.

## Files

| File | Content |
|---|---|
| `liquidacion_2026-04.csv` ... `liquidacion_2026-07.csv` | One settlement per period, each declaring its own offset |
| `publicidad_consola.csv` | Daily spend for four campaigns, before VAT |
| `facturas_publicidad.json` | Monthly ad invoice (subtotal = console total, VAT at 0.16) |
| `venta_erp.json` | Net revenue before VAT by order month, including sales not settled yet |
| `oraculo.json` | Expected answer per closing month and per boundary case |

Settlement layout: `key,value` preamble (`Periodo`, `Huso horario`, `Moneda`), a blank line,
then the 18-column header described in `skills/marketplace-expenses/amazon/specs/cierre_amazon.md`.
Amounts use a thousands separator when needed and are empty when zero. Timestamps are local
to the file's offset.

| Period | Declared offset |
|---|---|
| 2026-04 | `UTC-07:00` |
| 2026-05 | `UTC-07:00` |
| 2026-06 | `UTC-08:00` |
| 2026-07 | `UTC+00:00` |

The closing zone in the example config is `UTC-06:00`.

## Designed scenarios

- **Tail cohort** in May, June and July. Revenue pending at each month end equals exactly
  the tail that arrives the next month; July's pending revenue never settles inside the set.
- **Negative tail** in June: the three largest May orders are refunded early in June, so
  June's tail has negative net revenue (and May's provision is negative).
- **Advertising in three sources** every month: three VAT-inclusive settlement deductions,
  the console and the invoice. The settlement figure can differ by a cent from rounding.
- **Withholding out of band** in June: every other random sale in the June file is withheld
  at 0.16 instead of 0.08.
- **Boundary rows**, eight of them, placed by hand near month ends in all three offsets.
  Rows move forward (late evening in `UTC-07:00`/`UTC-08:00`) and backward (early morning in
  `UTC+00:00`). Two of them would land in the wrong month under a constant one-hour shift.
- Period charges: subscription, storage, a positive adjustment in May, and bank payouts
  (`Transferencia`) that are not expense but count in the settled total.

## `oraculo.json`

```text
parametros                    seed, months, offsets, closing zone, rates
meses[AAAA-MM]                filas, total_liquidado, venta_neta_cohorte_mes,
                              venta_neta_cola {origin month: amount},
                              tarifas_cohorte_mes / tarifas_cola {comision, logistica, otras_tarifas},
                              cargos_periodo {tipo: amount}, publicidad_sin_iva {liquidacion, consola, factura},
                              filas_publicidad_liquidacion, retencion {base, retenida}
venta_erp                     the ERP figures, repeated for convenience
casos_borde[]                 archivo, fila, pedido, huso, local timestamps, mes_liquidacion, mes_pedido,
                              desfase_fijo_de_una_hora_falla, esperado, nota
meses_retencion_fuera_de_banda, meses_cola_negativa, filas_fuera_de_meses, ventas_pendientes
```

Expense figures in the oracle use the expense sign (positive = cost to the seller).
